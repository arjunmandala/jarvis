A teammate you assign tickets to, not a tool you operate

Jarvis is a coding agent for the company. Assign a Linear issue to it and it behaves the way a careful engineer would: it reads the codebase, asks questions if the request is really a question, posts a plan as a comment, and waits. When a human replies approve, it writes the code inside an isolated cloud sandbox, runs the tests, pushes a branch, and opens a GitHub pull request. Then it stops: merging is a human's job, permanently.

Jarvis is glue, not an engine. It does not reimplement a planner, a debugger, or a review engine. It wires four existing systems together and owns only the connective tissue: a webhook receiver, a session store, an orchestrator state machine, the Linear ⇄ agent adapters, and the system prompts. Everything hard is delegated.

Six positions the code refuses to compromise on

Glue, not engine

If a mature system already does the job, Jarvis wires it in rather than rebuilding it. The repo's value is the seams, not the parts.

Two human gates

No plan is implemented without approval; no PR is merged by Jarvis, ever. Both gates are structural: they cannot be bypassed in code.

Fail loud

Every error path both logs and posts to Linear. A session that dies silently is worse than one that says exactly how it died.

Advisory everything

Memory, screenshots, symbol indexing, status nudges: every enhancement fails soft. A broken bonus never blocks a run.

Durable by issue

Work is keyed to the issue, not the session. Kill the sandbox, restart the host, re-assign the ticket: Jarvis resumes from the pushed branch and the saved plan, never from scratch.

Deliberate laziness

Regex before classifier, SQLite before ORM, one sandbox before a pool. Every shortcut carries a ponytail: comment naming its ceiling and its upgrade path.

One state machine, one sandbox, three channels

A · Lifecycle

The phase state machine

Every session is a row in SQLite walking this graph. A host restart loses nothing but live steering; boot reconciliation re-attaches to running sandboxes and replays their results.

clarify ─ chat loop: questions answered in place; a change request escalates ─▶ plan

plan ──▶ await_approval ⇄ plan     revision loop — any feedback that isn't approval
                │
                └─ approve ──▶ implement ──▶ done
                                    │
                                    └─ failure ──▶ error  fail loud, retry by re-assigning

done ⇄ review      question on a finished PR — report only, always returns to done
done ⇄ implement   change request on a finished PR — updates it in place, same branch

Which way a reply routes is decided by small, cheap Haiku classifiers on the host. Is this new issue a question or a change request? Is this follow-up a revision or a review ask? Each one is a raw API call that fails soft to the safest answer.

A plan can also come back as a decomposition: if the issue is too big, the planner returns a numbered split instead, and on approval Jarvis creates the sub-issues in Linear and assigns them to itself. Each one then runs this whole pipeline on its own.

B · Isolation

Where code executes

The target repo is cloned fresh into a new E2B sandbox for every phase that needs one. Untrusted generated code never touches the host.

Inside the sandbox the agent gets a normal developer's experience (it edits files, runs tests, starts servers, curls endpoints) and learns from real tool output instead of special plumbing. The work branch is deterministic (jarvis/<issueId>) and pushed to the remote before the agent even starts, then again after every meaningful step. A run that dies mid-implementation leaves recoverable work on the remote, and the next assignment resumes from it.

Host and sandbox speak over exactly three channels:

ChannelDirectionCarries
stdout · NDJSON sandbox → host Live telemetry (assistant text, tool calls, results) relayed to Linear activities in real time. Assumed unreliable.
/tmp/jarvis-result.json sandbox → host The authoritative final result. Streams go half-open; this file is what recovery trusts after a restart.
/tmp/jarvis-inbox.jsonl host → sandbox Mid-run steering. Comment on the issue while Jarvis works and the runner injects it into the live agent turn within ~2 seconds.

The stream is raced against a detached watcher that polls the result file and checks the runner process is alive, so a hung stream can never hang the host.

C · Tasks

Six jobs, one contract

Each task is a goal, a model, a tool list, and hard turn + budget caps, fed to the in-sandbox runner. The difference between them is the goal text, not bespoke machinery.

TaskModelTurnsJob
mapSonnet20One-time read-only survey of the repo, cached and injected into every later task.
planSonnet25Produce the plan a human will approve, returned verbatim to Linear.
reviseSonnet25Plan + human feedback → revised plan. Loops until approval.
implementSonnet / Opus120Approved plan → code, tests, pushes, gh pr create. Final message must be exactly the PR URL.
reviewSonnet40Self-review of large diffs, and on-demand PR review for follow-up questions.
chatSonnet15Answer a question about the issue or repo. Read-only tools, $1 cap.

Implementation routes its own model from the plan's fixed two-line Type: / Scope: header. A small non-refactor change runs on Sonnet at a $3 cap; anything large, and every refactor, runs on Opus at $8. A garbled header defaults to Opus: never a regression, just no saving.

D · Memory

What it remembers

Same-issue memory, assembled fresh for every run right after clone. Advisory end to end.

Two layers. The visible conversation (every Linear comment across every session on the issue, newest-first, capped at 20k characters) is appended to the task goal, so the agent always knows what was already said. The raw event streams of the last ten runs are exported into the sandbox as files the agent can grep on demand: what it tried before, what failed, what the tests said. If any of this breaks, the run simply proceeds memory-less.

Persistence is seven SQLite tables and no ORM: sessions, cached repo maps, runs, raw run events, phase-transition timings, cached Linear team states, and the auto-renewed OAuth token. The whole database also feeds npm run report, a failure-pattern and economics dashboard mined from what the agent actually did.

The decisions you only see up close

10-second rule
Linear marks an agent unresponsive after 10 seconds. Every webhook is acknowledged with a thought activity before any real work starts, and every error path posts an activity. A session never just goes quiet.
prompt-cache discipline
System prompt suffixes are byte-stable; per-run content (issue body, repo map, plan) goes in the goal instead, so the Agent SDK's prompt cache hits across every run. Bounded tasks also run at reduced reasoning effort to cut thinking-token spend.
approval is a regex
Deliberately. "Approve" and "stop" are keyword parsers, not classifiers; the known ceiling (sarcasm, odd phrasing) and the upgrade path are written next to the code. The subtler judgments (question vs. change, revise vs. review) do get a classifier, the cheapest one available.
the empty branch push
The work branch is pushed to the remote before the implementing agent runs a single turn. A run that dies in its first minute still leaves an assignable branch behind.
baked runner
The in-sandbox runner script is baked into the E2B template at build time, never uploaded per-run. The tradeoff is honest: change the runner, rebuild the template, or sandboxes silently run the old one.
steering by tail
Mid-run comments are base64-encoded, echoed onto an inbox file inside the sandbox, and picked up by a 2-second tail loop. No sockets, no message broker, nothing to reconnect after a restart.
cumulative accounting
The SDK reports usage for the final turn only; the runner sums every turn into a cumulative total, so the cost ledger reflects what a run actually spent.
screenshots ride along
Images pasted into Linear are downloaded host-side (capped at five images, 5 MB each) and handed to the agent as real image content. A failed download is skipped, never fatal.
status follows phase
The Linear issue's workflow state advances as Jarvis moves (planning, implementing, PR opened, done), matched by Linear's stable state categories rather than team-specific names. There is deliberately no "error" status: Jarvis won't fake a state it isn't confident about.
tokens renew themselves
The Linear app token is minted via OAuth client-credentials, stored in SQLite, renewed a day before its ~30-day expiry on a bounded backoff, and force-refreshed on any 401. No credentials rotate through .env.
re-assignment is resume
Re-assigning an issue mints a new session, so the orchestrator first looks for the newest prior session on the same issue: finished with a PR → point at it; interrupted mid-implement → resume the branch, no re-approval; planned but unapproved → re-post the plan. A prior still running refuses the duplicate outright.
plan recovery from Linear itself
If the local database ever loses a plan, a GraphQL fallback recovers the last one straight from Linear's activity history, identified by the approval footer every plan carries.
